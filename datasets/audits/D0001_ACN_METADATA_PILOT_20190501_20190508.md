## Time semantics

The web-export wrapper records its query boundaries in GMT, while each session declares `timezone = America/Los_Angeles`. In May 2019, the returned query corresponds approximately to local time from 2019-04-30 17:00 to 2019-05-07 17:00, not a local-midnight-to-local-midnight week.

This pilot therefore demonstrates that future formal acquisition must use explicit timezone-aware API windows. The web-interface file must not be treated as evidence that the selected dates were interpreted as local calendar boundaries.

## Interpretation for the current research question

This file can support:

- session-arrival and connection-window audits;
- requested departure and requested-energy coverage analysis;
- future-arrival branch prototypes based on session metadata;
- forecast-time leakage rules for revised `userInputs`;
- monthly coverage and station-activity diagnostics.

This file **cannot** support:

- active-session partial power-trajectory forecasting;
- measured-current or power aggregation;
- separation of measured current and pilot/setpoint control;
- station-level 15-minute power labels.

The absence of `chargingCurrent` and `pilotSignal` confirms that the web-interface export is metadata-only for this download. The `/ts` API endpoint or another metered dataset is required before Gate 1 can test the incremental value of active-session trajectories.
